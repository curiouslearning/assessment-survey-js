# Research: Spelling Assessment Analytics Reporting

## 1. Is the Firebase/BigQuery event path already type-agnostic?

**Question**: Does anything in the current `Assessment`/`AnalyticsIntegration` code path prevent Spelling assessment events from already reaching Firebase Analytics correctly?

**Finding**: No. `Assessment.handleAnswerButtonPress` (`src/assessment/assessment.ts:307`) calls `logPuzzleCompletedEvent` unconditionally on every answer (gated only by `bucketGenMode === RandomBST`, which is the mode every live assessment — including Spelling, per FM-978's requirement to reuse the existing binary-search algorithm — already uses). Both `TapToAnswerController` (`src/ui/tap-to-answer-controller.ts`) and `DragToAnswerController` (`src/ui/drag-drop/drag-to-answer-controller.ts`) — Spelling is the first assessment type to use the tap variant — invoke the identical `AssessmentUI.onAnswer` contract callback (`src/ui/assessment-ui.ts:6`), which `Assessment.setupUIHandlers()` (`assessment.ts:82-91`) wires to the same `handleAnswerButtonPress`. `logBucketCompletedEvent` and `LogCompletedEvent`/`onEnd()` are likewise reached through UI-agnostic, type-agnostic code paths.

**Decision**: User Story 1 (Firebase/BigQuery events) requires no new production code to make events *fire* — it requires (a) regression-test coverage proving the tap-to-answer path produces the same event as the drag path (nothing today asserts this), and (b) the one small addition below (§2) so events are *attributable* to Spelling once queried in BigQuery (User Story 3).

**Alternatives considered**: Adding an explicit `assessmentType` branch inside `handleAnswerButtonPress`/`logPuzzleCompletedEvent` — rejected as unnecessary; the events already fire identically regardless of type, so branching would only add risk of accidentally diverging Spelling's event shape from other types (violating FR-001/FR-012).

## 2. How should Spelling events become distinguishable in BigQuery (FR-008)?

**Question**: What field, if any, lets an analyst filter "Spelling only" out of the shared `answered`/`bucketCompleted`/`completed` event stream?

**Finding**: No existing field does this reliably. `CommonEventProperties.app` and `.lang` (`src/analytics/analytics-event-interface.ts:4-25`) are derived from the data URL's naming convention (`getAppTypeFromDataURL`/`getAppLanguageFromDataURL`, `src/utils/urlUtils.ts:74-102` — last/second-to-last hyphen-delimited segment of the URL), not from the assessment JSON's `assessmentType` field, and are not guaranteed unique per assessment type.

**Decision**: Extend the existing "common analytics properties" module (`src/utils/AnalyticsUtils.ts`) — which already holds `cr_user_id`, `language`, `app`, `user_source`, `content_version`, `app_version` as module-level state set once via `setCommonAnalyticsEventsProperties(...)` — with one more field, `assessmentType`. Because `AnalyticsIntegration.createBaseEventData()` (`src/analytics/analytics-integration.ts:32-43`) already spreads `getCommonAnalyticsEventsProperties()` into **every** tracked event automatically, this single addition makes `assessmentType` appear on `Opened`, `UserLocation`, `Initialized`, `Answered`, `BucketCompleted`, and `Completed` alike, for **every** assessment type (not just Spelling) — satisfying FR-008 (distinguishable) and FR-012 (purely additive, uniform) at once, with no change needed inside `assessment.ts`'s three tracking call sites.

`App.ts` already reads the raw value at `initializeGame()` (`App.ts:315`, `const assessmentType = data['assessmentType'];`) and already forwards it to the UI layer (`App.ts:345`). It needs one more forwarding edge: into `setCommonProperties()` → `setCommonAnalyticsEventsProperties(...)` (`App.ts:405-413`), which currently doesn't receive it.

**Alternatives considered**:
- Threading `assessmentType` through `Assessment`'s constructor and duplicating it into each of the three `track()` call sites — rejected: three edit points instead of one, and inconsistent with `Opened`/`Initialized`/`UserLocation` (fired from `App.ts`, not `Assessment`) which would then lack the field entirely.
- A Spelling-only special-cased field/event — rejected: violates the spec's explicit requirement that this be additive and uniform across types, and duplicates the `app`/`lang` pattern's own known limitation.

## 3. How does `Assessment` learn whether the current session is a Spelling session (for the Firestore gate)?

**Question**: FR-006/FR-010 require the Firestore completion write to happen "when — and only when" a Spelling assessment completes. `Assessment` needs to read the assessment type at that decision point.

**Finding**: `Assessment` already captures a snapshot of the common properties object once, in `startAssessment()` (`assessment.ts:209-210`, `this.commonProperties = getCommonAnalyticsEventsProperties();`), and already reads back off that same snapshot later in `LogCompletedEvent()` (`assessment.ts:748,751`, `this.commonProperties?.cr_user_id`, `this.commonProperties?.app`). Once §2's `assessmentType` field is added to the common-properties module, `this.commonProperties.assessmentType` becomes available at exactly the point (`LogCompletedEvent`, called from `onEnd()`) where the Firestore write needs to be gated — no constructor change, no new instance field, no new plumbing.

**Decision**: Gate the Firestore write in `LogCompletedEvent()` on `this.commonProperties?.assessmentType === 'spelling'`, matching the existing inline-string-literal style already used for the same comparison in `src/ui/drag-drop/dragdrop-ui.ts` (`assessmentType === 'spelling'`) — no new shared constant is introduced for a single literal, consistent with the codebase's current convention (and consistent with FM-981, the type-scaffold ticket, not having landed yet / not having introduced a typed enum).

**Alternatives considered**: Adding a 4th constructor parameter to `Assessment` — rejected as redundant once the common-properties snapshot already carries the value at the point it's needed, and it would require editing the `new Assessment(...)` call site and every existing test that constructs `Assessment` directly.

## 4. How is a Firestore client obtained, given no Firestore integration exists today?

**Question**: `@curiouslearning/analytics@1.3.1` (the SDK wrapper `AnalyticsIntegration` builds on) exposes only `FirebaseStrategy` and `StatsigStrategy` — no Firestore strategy. The app has a direct `firebase@^9.12.1` dependency, but `@curiouslearning/analytics` nests its own nested nested copy of `firebase@^11.4.0` (`node_modules/@curiouslearning/analytics/node_modules/firebase`). Can/should this feature reuse the Firebase App instance `AnalyticsIntegration`/`FirebaseStrategy` already creates?

**Finding**: `BaseAnalyticsIntegration.firebaseApp` (`src/analytics/base-analytics-integration.ts:131-133`) exposes `firebaseStrategy.firebaseApp`, but that instance is constructed internally by `@curiouslearning/analytics`'s own nested `firebase@^11.4.0` copy — a different, isolated package instance from the app's own top-level `firebase@^9.12.1`. Passing an app object created by one major version of the modular Firebase SDK into another major version's `getFirestore()` is unsupported and risks subtle runtime incompatibilities (the modular SDK identifies "kind" via internal `_delegate`/component registration that isn't guaranteed stable across majors).

**Decision**: Initialize a **separate, independently-named Firebase App** using the app's own top-level `firebase@^9.12.1` dependency (`firebase/app`'s `initializeApp(firebaseConfig, 'assessment-survey-firestore')`, `firebase/firestore`'s `getFirestore(app)`), reusing the same project config object (`firebaseConfig` from `src/analytics/analytics-config.ts` — same Firebase project, so writes land in the same project as the Analytics events). A distinct app name avoids any `"Firebase App named '[DEFAULT]' already exists"` collision; since it lives in a different package instance from `@curiouslearning/analytics`'s nested copy, there is no shared app registry between the two anyway, but the explicit name also protects against double-initialization if `initializeFirestore()` is ever called more than once within our own code (idempotency handled by an internal singleton, mirroring `AnalyticsIntegration`'s own `initializeAnalytics()`/`getInstance()` pattern).

No dependency version bump is required: `firebase@9.x`'s modular `firebase/firestore` API (`getFirestore`, `collection`, `addDoc`, `serverTimestamp`) is complete and stable; nothing in this feature needs a `firebase@11`-only API.

**Alternatives considered**:
- Bumping the app's direct `firebase` dependency to `^11` to match `@curiouslearning/analytics`'s nested copy — rejected as unnecessary scope for this ticket (a dependency major-version bump has its own blast radius across the legacy `firebase/analytics` usage in `analyticsEvents.ts` and `standalone.ts`) and not required to satisfy any FR here.
- Requesting a `FirestoreStrategy` addition to `@curiouslearning/analytics` upstream — desirable long-term (would let `AnalyticsService`/`AnalyticsIntegration` own Firestore the same way it owns Firebase Analytics), but that package is an external dependency this ticket does not control the release cycle of; blocking FM-986 on an upstream package change is not warranted when a small, local, self-contained module fully satisfies the spec today.
- Reusing the legacy `AnalyticsEvents`/`firebase/analytics` `gana` app instance — rejected: `AnalyticsEvents.linkAnalytics()` (the only setter for `gana`) is not called anywhere in current `src/`, so `gana` is always `undefined` at runtime; building new functionality on a dormant/dead code path would silently fail.

## 5. Structure of the new Firestore module

**Decision**: `src/analytics/firestore-integration.ts`, a class `FirestoreIntegration` mirroring `AnalyticsIntegration`'s existing shape for consistency (Constitution Principle III — SOLID; this is a stateful, identity-based integration, same category as `AnalyticsIntegration`):
- `static initializeFirestore(config: AnalyticsConfig = firebaseConfig): void` — synchronous (Firestore's modular `getFirestore()` does not require awaiting; only individual document operations are async), builds the singleton once.
- `static getInstance(): FirestoreIntegration` — throws if not yet initialized, matching `AnalyticsIntegration.getInstance()`'s contract exactly (same error-handling shape `Assessment`'s constructor already defends against via try/catch).
- `writeCompletionRecord(record: SpellingAssessmentCompletionRecord): void` — fire-and-forget: internally calls `addDoc(...)` and attaches a `.catch()` that only `console.error`s, never rejecting/throwing back to the caller. This directly satisfies FR-009 (a write failure must not affect the learner's experience or block the Firebase `completed` event) without requiring call sites to wrap every call in try/catch.

**Call site**: `App.spinUp()` (`App.ts:162-169`), immediately after `AnalyticsIntegration.initializeAnalytics`/`getInstance()`, inside the same `if (config.analyticsConfig)` block and `try/catch` — reuses the same config object, same "only if analytics is configured at all" gate, no new `AppStartupConfig` field. `Assessment`'s constructor defensively resolves `FirestoreIntegration.getInstance()` in a `try/catch` exactly like it already does for `AnalyticsIntegration` (`assessment.ts:75-79`), so tests that construct `Assessment` without initializing Firestore continue to work unchanged (the field is simply `null`, and the gated write in `LogCompletedEvent()` no-ops via `?.`).

## 6. Document shape and collection naming

**Decision**: Collection `assessmentCompletions` (not `spellingCompletions`) — forward-compatible naming since the write already carries an `assessmentType` field for filtering (consistent with FR-008's "one attribute, uniformly applied" principle, and avoids a rename if a future ticket extends the same mechanism to other assessment types, per the spec's Assumptions). One document per completed session, fields: `clUserId`, `assessmentType`, `lang`, `score`, `maxScore`, `basalBucket`, `ceilingBucket`, plus a server-generated `completedAt` (`serverTimestamp()`) — mirrors exactly the data already computed in `LogCompletedEvent()` for the Firebase `Completed` event (`score`, `maxScore`, `basalBucketID`, `ceilingBucketID`) plus the identity/context fields already available on `this.commonProperties`. No document-ID scheme beyond Firestore's auto-generated ID is needed for idempotency: `LogCompletedEvent()` is reached exactly once per session through the existing single-call `onEnd()` lifecycle hook (no retry path exists that could invoke it twice), so FR-011 ("not more than one record per session") holds by construction rather than requiring a dedup key.

## 7. Testing approach

**Decision**: Follow the exact precedent in `test/analytics/analyticsIntegration.test.ts` and `test/analytics/analyticsEvents.test.ts`: `jest.mock('firebase/app', () => ({ initializeApp: jest.fn() }))` and a new `jest.mock('firebase/firestore', () => ({ getFirestore: jest.fn(), collection: jest.fn(), addDoc: jest.fn(), serverTimestamp: jest.fn() }))` at module scope in a new `test/analytics/firestoreIntegration.test.ts`, resetting the module's private static `instance` between tests the same way `analyticsIntegration.test.ts` does (`(FirestoreIntegration as any).instance = null`). `test/assessment/assessment.test.ts` gains: (a) a happy-path scenario asserting `logPuzzleCompletedEvent`-equivalent behavior is identical whether reached via the existing `onAnswer` callback (already effectively covers both UI adapters, since the callback signature is UI-agnostic), and (b) a new `describe('Firestore completion recording')` block asserting `writeCompletionRecord` is called once with the expected shape when `commonProperties.assessmentType === 'spelling'`, and not called otherwise. `test/utils/AnalyticsUtils.test.ts` (if it exists) or a new equivalent gains a case asserting `assessmentType` round-trips through `setCommonAnalyticsEventsProperties`/`getCommonAnalyticsEventsProperties`.

## 8. Out-of-scope items noted but not addressed

- `AnalyticsIntegration.sendDataToThirdParty`'s existing call site in `assessment.ts` (`LogCompletedEvent`) passes `this.commonProperties?.app` as the `assessmentType` parameter, not the actual assessment type — a pre-existing defect in the third-party (Synapse) XHR integration, unrelated to Firebase/BigQuery/Firestore reporting and outside FM-986's acceptance criteria. Left unchanged; flagged here for visibility.
- `bucketCompleted`/`answered` events firing only under `BucketGenMode.RandomBST` (not `LinearArrayBased`) is pre-existing, shared behavior across all assessment types (a developer-tooling mode), not something Spelling introduces or that FM-986 asks to change (see spec.md Edge Cases).
